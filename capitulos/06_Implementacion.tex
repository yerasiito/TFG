\chapter{Implementación}
Este capítulo describe en detalle el proceso de implementación llevado a cabo en \Gls{snapperml}, con énfasis en las soluciones técnicas adoptadas para abordar la \gls{deuda} y el diseño de la interfaz web. La sección se organiza en dos partes principales: la configuración inicial del entorno de desarrollo y las estrategias utilizadas para resolver los desafíos técnicos. Además, se detalla el desarrollo de la interfaz de usuario, explicando la estructura del proyecto y los componentes clave que permiten la interacción eficiente con \Gls{snapperml}.

\section{Configuración inicial}
La configuración inicial es el paso previo para garantizar un entorno de desarrollo estable y eficiente en SnapperML. Este proceso incluye la preparación del entorno, la selección de herramientas adecuadas y la configuración específica del sistema, elementos esenciales para optimizar el flujo de trabajo y asegurar una ejecución fluida de las distintas funcionalidades del proyecto.

\subsection{Entorno de desarrollo}

Para el desarrollo de \Gls{snapperml}, he elegido \acrfull{vsc} como mi \Gls{ideg}. Esta elección no fue al azar, ya que \acrlong{vsc} ofrece una combinación única de rendimiento, extensibilidad y soporte para múltiples lenguajes y herramientas, lo que lo convierte en una opción ideal para proyectos complejos como \Gls{snapperml}. A continuación, se detallan las razones por las cuales opté por \acrshort{vsc} en lugar de otros \Glspl{ideg} populares, como PyCharm:

\begin{itemize}
    \item \textbf{Rendimiento y Ligereza}: A diferencia de PyCharm, que puede ser pesado y consumir más recursos del sistema, \acrshort{vsc} es un \Gls{ideg} ligero que ofrece un rendimiento fluido, incluso en máquinas con especificaciones moderadas. Esto es especialmente importante cuando se trabaja con proyectos de machine learning que ya requieren una cantidad significativa de recursos para ejecutar experimentos y modelos.
    \item \textbf{Extensibilidad y Plugins}: \acrlong{vsc} destaca por su extensibilidad a través de una amplia variedad de extensiones. Pude personalizar mi entorno de trabajo instalando plugins esenciales como \textit{Python} para soporte de sintaxis y depuración, \textit{Docker} para gestionar contenedores, \textit{\acrshort{yaml}} para la edición de archivos de configuración, y \textit{debugpy} para integrar la depuración de Python. Esta flexibilidad me permitió adaptar el \Gls{ideg} a las necesidades específicas de \Gls{snapperml}.

    \item \textbf{Integración con Docker y Contenedores}: La extensión de Docker en \acrshort{vsc} facilita la gestión y ejecución de contenedores directamente desde el \Gls{ideg}. Esto fue de ayuda para el desarrollo de \Gls{snapperml}, donde las bases de datos y la interfaz de MLflow se ejecutan en contenedores Docker. Con \acrshort{vsc}, pude controlar los contenedores, inspeccionar los registros y solucionar problemas rápidamente.

    \item \textbf{Depuración Avanzada}: \acrshort{vsc}, junto con \texttt{debugpy}, ofrece una experiencia de depuración potente y personalizable. Esto fue fundamental para resolver la \gls{deuda} del proyecto, que requería un análisis detallado del comportamiento del código y la identificación de errores complejos. La capacidad de configurar múltiples escenarios de depuración me permitió investigar a fondo las diferentes partes de \Gls{snapperml} y optimizar su ejecución.

    \item \textbf{Soporte para Lenguajes Múltiples}: \Gls{snapperml} involucra varios lenguajes y tecnologías, como Python, \acrshort{yaml}, Docker, y más. \acrshort{vsc} proporciona un soporte excelente para todos estos lenguajes en un solo \Gls{ideg}, eliminando la necesidad de cambiar entre diferentes herramientas y mejorando mi flujo de trabajo.

    \item \textbf{Git Integrado}: \acrshort{vsc} tiene integración nativa con Git, lo que facilitó el control de versiones y la colaboración en el proyecto. Pude realizar cambios, gestionar ramas y resolver conflictos de manera eficiente sin salir del entorno de desarrollo.

    \item \textbf{Personalización y Configuración del Entorno}: \acrshort{vsc} permite una personalización completa a través del archivo \texttt{settings.json}, donde configuré opciones específicas como el autoformateo al guardar y la gestión de entornos virtuales. Esto contribuyó a mantener un código limpio y a seguir las mejores prácticas de desarrollo.
\end{itemize}

\subsection{Configuración del Debugger}

La configuración del \textit{debugger} en el desarrollo de \Gls{snapperml} presentó varios desafíos debido a la naturaleza del framework. Dado que \Gls{snapperml} se ejecuta principalmente desde la línea de comandos (\Gls{clig}) y no como un módulo de Python estándar, la depuración no era un proceso directo. La depuración de un proyecto ejecutado desde la \Gls{clig} requiere un archivo especial de \textit{entry point} denominado \texttt{run\_experiment.py}. Sin embargo, al intentar lanzar el \textit{debugger} utilizando este archivo, me encontré con que no se ejecutaba correctamente: no se imprimía nada en pantalla ni se lanzaba la ejecución de \Gls{snapperml}.

Para resolver este problema, comencé una búsqueda intensiva en Stack Overflow, donde revisé publicaciones similares como esta \cite{stackoverflow_modules}. Sin embargo, las soluciones propuestas no se aplicaban directamente a mi caso porque \Gls{snapperml} no está estructurado como un módulo de Python tradicional. Dado que estas respuestas no eran adecuadas, publiqué mi propia pregunta en Stack Overflow titulada: \textbf{How to debug CLI Python package in \acrshort{vsc}?}. El post completo con detalles y contexto se encuentra en el Anexo \ref{Anexo A}.

Aunque aún no había recibido respuestas, logré encontrar una solución preliminar por mi cuenta. Configuré el \textit{debugger} en \acrfull{vsc} usando \texttt{debugpy}, una extensión integrada para la depuración de Python. La primera configuración que utilicé fue la siguiente:

\begin{minted}{json}
{
    "configurations": [
        {
            "name": "Debug snapper-ml CLI",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/.venv/bin/snapper-ml", 
            "args": [
                "--config_file",
                "examples/experiments/svm.\acrshort{yaml}"
            ],
            "console": "integratedTerminal",
            "cwd": "${workspaceFolder}",
            "envFile": "${workspaceFolder}/.env",
        }
    ]
}
\end{minted}
\mycaptionof{listing}{Primera configuración para depurar \Gls{snapperml} con \texttt{debugpy}}

Esta configuración permitió que \acrshort{vsc} lanzara \Gls{snapperml} desde la \Gls{clig}, especificando el archivo de configuración de experimentos \texttt{svm.\acrshort{yaml}}. Sin embargo, la solución aún presentaba ciertos problemas, ya que los errores de ejecución diferían al depurar, lo que complicaba la identificación y solución de problemas. Después de una exhaustiva búsqueda de soluciones y varias pruebas sin éxito, un comentario en mi publicación de Stack Overflow me redirigió a un post relacionado \cite{stackoverflow_first_solution}.

Resultó que para que el \textit{entry point} se ejecutara correctamente, era necesario añadir un bloque específico de Python que iniciara el script de manera adecuada:

\begin{minted}{python}
# run_experiment.py <= entry point
if __name__ == '__main__':
    app() 
\end{minted}
\mycaptionof{listing}{Modificación del entry point para depurar}
\begin{minted}{json}
{
    "configurations": [
        {
            "name": "Debug from entry point snapper-ml CLI",
            "type": "debugpy",
            "request": "launch",
            "program": "${workspaceFolder}/snapper_ml/scripts/run_experiment.py",
            "args": [
                "--config_file",
                "examples/experiments/svm.\acrshort{yaml}"
            ]
        }
    ]
}
\end{minted}
\mycaptionof{listing}{Segunda configuración para depurar \Gls{snapperml}}

Esta modificación aseguraba que \texttt{run\_experiment.py} actuara correctamente como \textit{entry point}. Después de ajustarlo, marqué mi pregunta en Stack Overflow como duplicada y publiqué una respuesta detallada en la pregunta original \cite{stackoverflow_first_solution}. En esa respuesta, describí cómo resolví el problema, incluyendo el código y las instrucciones para configurar el \textit{debugger}. Finalmente añadí una última configuración para ejecutar ficheros directamente ya que me permitía arreglar otro tipo de errores:

\begin{minted}{json}
{
    "configurations": [
        {
            "name": "Python Debugger: train_svm.py file",
            "type": "debugpy",
            "request": "launch",
            "program": "train_svm.py",
            "console": "integratedTerminal",
            "args": [
                "examples/experiments/svm.\acrshort{yaml}"
            ],
        }
    ]
}
\end{minted}
\mycaptionof{listing}{Tercera configuración para depurar \Gls{snapperml}}

Gracias a estas configuraciones, pude depurar \Gls{snapperml} de manera eficiente, ya sea ejecutando directamente desde la \Gls{clig}, utilizando el \textit{entry point} o directamente un fichero con todas las validaciones necesarias.

\section{Resolviendo la Deuda Técnica}
En el capítulo de \textbf{Diseño \ref{diseño}} se ha hablado en profundidad sobre la \gls{deuda} y los problemas encontrados. En esta sección se detallará el proceso de resolución de dicha deuda.

\subsection{Archivos de configuración inválidos}
Uno de los problemas identificados en \Gls{snapperml} está relacionado con la configuración de variables de entorno, necesarias para ejecutar el proyecto tanto en un entorno Docker como en una máquina local. En el archivo docker-compose.yaml, se hace referencia a un archivo .env, pero se encontró que ciertas variables de entorno requeridas por MLflow no estaban definidas en este archivo.

\vspace{2.5mm}

Para resolver este problema, se crearon dos archivos de entorno: uno para Docker (.envdocker) y otro para la máquina local (.env). El archivo .envdocker define las variables necesarias para que los servicios de MySQL y PostgreSQL se comuniquen dentro de la red de los contenedores Docker, mientras que el archivo .env está configurado para conexiones locales, utilizando 127.0.0.1 como host en lugar de los nombres de los contenedores. Esta solución permite ejecutar \Gls{snapperml} en ambos entornos sin problemas de configuración.

\vspace{2.5mm}

A continuación se muestra el contenido del archivo .envdocker para el entorno Docker:
\begin{minted}[breaklines]{bash}
MYSQL_ROOT_PASSWORD=root_password
MYSQL_DATABASE=mlflow_db
MYSQL_USER=mlflow_user
MYSQL_PASSWORD=mlflow_password
MYSQL_PORT=3306

POSTGRES_USER=optuna_user
POSTGRES_PASSWORD=optuna_password
POSTGRES_DB=optuna_db
POSTGRES_PORT=5432

MLFLOW_TRACKING_URI=mysql+mysqldb://${MYSQL_USER}:${MYSQL_PASSWORD}@mlflow_stor
age:${MYSQL_PORT}/${MYSQL_DATABASE}

MLFLOW_BACKEND_STORE_URI=postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@opt
una_storage:${POSTGRES_PORT}/${POSTGRES_DB}

MLFLOW_ARTIFACT_ROOT=/mnt/mlruns

OPTUNA_STORAGE_URI=postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@optuna_st
orage:${POSTGRES_PORT}/${POSTGRES_DB}
\end{minted}
\mycaptionof{listing}{Archivo de variables de entorno \texttt{.envdocker}}

Esta configuración de archivos permite levantar los contenedores Docker sin problemas de conexión y facilita la ejecución de \Gls{snapperml} tanto en entornos Docker como locales. Ahora es posible visualizar la interfaz de usuario de MLflow accediendo a \code{localhost:5000}.

\subsubsection{Flask-CORS}
Flask-CORS permite manejar el \Gls{cors} en aplicaciones web desarrolladas con Flask. En \Gls{snapperml}, esta librería es crucial cuando la interfaz web o API del sistema necesita interactuar con recursos ubicados en diferentes dominios o servidores. \Gls{cors} es una política de seguridad que restringe las solicitudes HTTP entre dominios distintos; por tanto, Flask-CORS permite habilitar o restringir estas solicitudes de forma controlada. Esto asegura que las aplicaciones externas o clientes distribuidos puedan acceder a los datos de experimentación en \Gls{snapperml} de manera segura, mejorando la interoperabilidad del sistema en entornos distribuidos.

\subsubsection{Pydantic-Settings} 
Pydantic-Settings es una extensión de la popular librería Pydantic, introducida en la versión 2, que facilita la validación de configuraciones y variables de entorno. En \Gls{snapperml}, esta librería es fundamental para garantizar que las configuraciones de experimentos, como las de MLflow y Optuna, sean correctas antes de ejecutarse, lo que reduce la probabilidad de errores durante la ejecución. La validación de configuraciones asegura que todos los parámetros estén en el formato esperado y dentro de un rango permitido, lo cual es especialmente útil en entornos de experimentación, donde los parámetros suelen cambiar con frecuencia. La falta de esta dependencia impide que el sistema valide correctamente las configuraciones, generando fallos al iniciar los experimentos.

\subsubsection{Ruamel.yaml} Ruamel.yaml es un parser avanzado para archivos \acrshort{yaml}, que permite una manipulación precisa de configuraciones almacenadas en este formato. \Gls{snapperml} utiliza Ruamel.yaml para cargar y editar configuraciones de experimentos de machine learning que suelen ser extensas y complejas. A diferencia de otros parsers \acrshort{yaml}, Ruamel.yaml permite conservar el orden de las claves y los comentarios en los archivos, lo cual es útil para preservar la legibilidad y facilitar futuras ediciones. Esta librería mejora la experiencia de los usuarios que necesitan ajustar configuraciones con frecuencia, manteniendo la consistencia y estructura del archivo.

En \Gls{snapperml}, esta librería facilita la comunicación entre el sistema y los usuarios al enviar notificaciones en tiempo real cuando un experimento comienza o finaliza. Esto es especialmente útil para experimentos de larga duración, ya que permite a los usuarios estar al tanto del progreso sin necesidad de monitorear constantemente la interfaz. En \Gls{snapperml}, estas dependencias permiten almacenar y gestionar datos de experimentos en bases de datos relacionales, facilitando la organización y persistencia de resultados en un entorno estructurado y accesible. PostgreSQL y MySQL son populares por su robustez y escalabilidad, lo cual hace que \Gls{snapperml} pueda manejar grandes volúmenes de datos de experimentación y seguimiento de modelos. \subsection{Dependencias Innecesarias}
Al revisar el código de \Gls{snapperml}, se identificó el uso de la librería \code{numpy} en situaciones donde librerías estándar de Python, como \code{random} y \code{float}, podrían cumplir con la misma funcionalidad. Si bien \code{numpy} es una librería muy útil para operaciones matemáticas avanzadas, en este caso su inclusión resultaba innecesaria dado que las funcionalidades que se utilizaban podían ser cubiertas por librerías nativas de Python. Al eliminar \code{numpy} en estas secciones del código, se reduce el tamaño de las dependencias y se simplifica el proceso de instalación del proyecto.
\begin{minted}{python}
#mlflow.py
try:
    import numpy as np
    patches.append(_get_seed_initializer_patch(target, np.random, 'Numpy', 'seed'))
except ModuleNotFoundError:
    pass
\end{minted}
\captionof{listing}{Uso innecesario de \texttt{numpy} para inicializar semillas en \texttt{mlflow.py}.}
\begin{minted}{python}
# experiments.py
concurrent_workers_by_gpu = available_gpus / gpu if gpu else np.inf
\end{minted}
\mycaptionof{listing}{Uso de \texttt{numpy} para definir \texttt{infinito} en \texttt{experiments.py}.}

En ambos casos, la funcionalidad que numpy proporciona puede ser sustituida por librerías estándar de Python, como random y float, que están preinstaladas en cualquier entorno Python y no requieren la instalación de paquetes externos.
\begin{minted}{python}
#mlflow.py
try:
    patches.append(_get_seed_initializer_patch(target, random, 'Numpy', 'seed'))
except ModuleNotFoundError:
    pass
\end{minted}
\captionof{listing}{Reemplazo de \texttt{numpy} por la librería estándar \texttt{random} para inicializar semillas.}
\begin{minted}{python}

\end{minted}

\subsubsection*{Motivos para Preferir Librerías Estándar sobre Dependencias Externas} Optar por librerías estándar en lugar de dependencias externas como numpy presenta varias ventajas, especialmente en casos donde la funcionalidad que se requiere es básica y puede ser satisfecha sin necesidad de instalaciones adicionales. A continuación, se detallan los motivos principales:

\begin{itemize} \item \textbf{Reducción del Tamaño del Proyecto}: numpy es una librería extensa que introduce un considerable tamaño adicional al proyecto. Al evitar su inclusión cuando no es esencial, el peso del proyecto se reduce, lo cual beneficia a usuarios y desarrolladores que descargan e instalan el sistema, especialmente en entornos con limitaciones de almacenamiento o ancho de banda.

    \item \textbf{Simplificación de Instalación y Dependencias}: Cada dependencia externa añade complejidad al proceso de instalación, ya que se deben gestionar versiones compatibles y evitar conflictos entre paquetes. Al utilizar únicamente librerías estándar, se elimina esta complejidad, reduciendo los posibles problemas de compatibilidad y simplificando la configuración del entorno.

    \item \textbf{Aumento de la Portabilidad del Código}: Al depender exclusivamente de librerías estándar, el código se vuelve más portable. Esto significa que el sistema puede ser ejecutado en una variedad de entornos sin requerir configuraciones adicionales ni instalaciones de paquetes, facilitando su implementación en sistemas nuevos y entornos controlados.

    \item \textbf{Facilidad en el Mantenimiento del Proyecto}: Menos dependencias implican menos elementos que deben actualizarse o mantenerse a largo plazo. Al depender de funcionalidades estándar de Python, se garantiza que el código seguirá siendo compatible con futuras versiones de Python, minimizando la necesidad de realizar ajustes ante cambios en las librerías externas.

\end{itemize}

En el caso de \Gls{snapperml}, la decisión de utilizar random y float en lugar de numpy para operaciones sencillas de generación de números aleatorios y valores de infinito contribuye a un sistema más ligero, portable y fácil de mantener. Este cambio, aunque sencillo, facilita la experiencia de instalación y reduce el peso del proyecto, lo que resulta en una mayor eficiencia y simplicidad para los usuarios y desarrolladores.

\subsection{Automatización del Entorno}
Para facilitar la configuración y gestión del entorno de desarrollo en SnapperML, se implementó un Makefile que automatiza la creación del entorno virtual, la instalación de dependencias, la ejecución de ejemplos, la gestión de contenedores Docker y la limpieza de archivos compilados. Esta automatización permite a los usuarios configurar y ejecutar el proyecto de forma rápida y consistente, reduciendo los errores asociados con la configuración manual y mejorando la eficiencia del flujo de trabajo.

El uso de un Makefile estandariza las tareas de desarrollo y asegura que todos los usuarios trabajen bajo las mismas condiciones, independientemente del entorno en el que se encuentren. Además, permite una integración sencilla con sistemas de CI/CD, facilitando así el despliegue y pruebas automatizadas. A continuación, se muestra el contenido del Makefile actualizado:

\begin{minted}{make}
.PHONY: install clean venv help run_example_svm UI docker stop_docker

venv:
	python3 -m venv $(VENV_DIR)

install: venv
	$(VENV_BIN)/pip install -e .
	$(VENV_BIN)/pip install -r requirements.txt

run_example_svm: install
    $(VENV_BIN)/snapper-ml --config_file=examples/experiments/svm.yaml

docker:
    @if ! docker info > /dev/null 2>&1; then \
        echo "Docker is not active. Attempting to start it..."; \
        sudo systemctl start docker || (echo "Failed to start Docker. Please start it manually." && exit 1); \
    fi
    @if [ "$(BACKGROUND)" = "1" ]; then \
        (cd docker && docker compose up -d); \
    else \
        (cd docker && docker compose up); \
    fi

stop_docker:
    @(cd docker && docker compose down)

clean:
	find . -type f -name "*.py[co]" -delete
	find . -type d -name "__pycache__" -delete
	rm -rf $(VENV_DIR)
\end{minted}

\vspace{4mm}

\vspace{2.5mm}

\subsection{Refactorizaciones}
A lo largo del proceso de optimización y mantenimiento de SnapperML, se llevaron a cabo varias refactorizaciones estratégicas con el objetivo de mejorar la calidad general del código, optimizar el uso de recursos y facilitar la detección y resolución de problemas. \subsubsection{Migración de \texttt{setup.py} a \texttt{pyproject.toml}}
Uno de los cambios fundamentales fue la migración de setup.py a pyproject.toml, en línea con las mejores prácticas modernas de empaquetado en Python. pyproject.toml se ha convertido en el estándar para definir la configuración de empaquetado y las dependencias de los proyectos Python, permitiendo una mejor integración con herramientas modernas como poetry y pip. Además, pyproject.toml mejora la portabilidad y reproducibilidad del proyecto, ya que unifica las configuraciones en un solo archivo.

\subsubsection{Importación Selectiva de Atributos}
Para optimizar el consumo de memoria y mejorar la eficiencia, se implementaron importaciones selectivas en módulos clave. Anteriormente, el proyecto realizaba importaciones globales utilizando from typing import *, lo cual incrementaba innecesariamente el uso de memoria al cargar todos los atributos de typing, incluso aquellos que no eran necesarios. Al cambiar a una importación selectiva de sólo los atributos específicos utilizados en el código, como Any, Dict, Tuple, TypeVar, Union, List, y Callable, se reduce significativamente la cantidad de memoria consumida por el módulo. \subsection{Problemas Durante la Implementación}

\subsubsection{\Gls{corsg}}
\acrfull{cors} es un mecanismo de seguridad implementado en los navegadores que restringe cómo los recursos de una página web pueden ser solicitados desde un dominio diferente al que sirvió la página. En otras palabras, si una aplicación web desea interactuar con una API que se encuentra en un dominio diferente, es necesario gestionar adecuadamente las políticas de \Gls{corsg} para evitar errores de bloqueo.

Para resolver los problemas de \Gls{corsg} en \Gls{snapperml}, se consideraron dos soluciones principales:
\begin{enumerate}
    \item Instalar y Configurar \texttt{flask\_cors}: Una solución rápida y efectiva fue utilizar el paquete \texttt{flask\_cors}, que simplifica el manejo de estas políticas en aplicaciones Flask. Se añadió el siguiente fragmento de código para permitir solicitudes desde diferentes orígenes:
          \begin{minted}{python} 
from flask_cors import CORS
CORS(app, allow_headers=["Content-Type", "Authorization"], methods=["POST", "OPTIONS"]) 
    \end{minted}
          Este enfoque es sencillo de implementar y útil para entornos de desarrollo o APIs que requieren flexibilidad en sus políticas de \Gls{corsg}.

    \item Configuración con Nginx: Una solución más robusta y adecuada para entornos de producción fue utilizar Nginx como servidor proxy inverso, configurando manualmente las políticas de \Gls{corsg}. Se utilizó el siguiente fragmento de configuración:
          \begin{minted}{bash} 
 server { 
    listen 80; 
    server_name localhost;
    location / {
        proxy_pass http://localhost:4000/;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header Host $http_host;
        proxy_pass_request_headers on;
    }
    
    location /execute/ {
        proxy_pass http://localhost:5000/;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header Host $http_host;
        proxy_pass_request_headers on;
    }
    
    error_page 500 502 503 504 /50x.html;
    location = /50x.html {
        root /usr/share/nginx/html;
    }
 }
    \end{minted}
\mycaptionof{listing}{Configuración de Nginx para evitar el CORS}
          Tras realizar esta configuración, fue necesario reiniciar Nginx con el comando \texttt{systemctl restart nginx} para que los cambios surtieran efecto.
\end{enumerate}

\subsubsection{Buffers y Sincronización}
Otro desafío surgió al gestionar los procesos de la API que ejecutan comandos en \Gls{snapperml}. Cuando se inicia un proceso desde la API, este se ejecuta y bloquea la API hasta que finaliza la ejecución. Para manejar la salida de los procesos en tiempo real, se implementó un generador que monitorea tanto la salida estándar (\texttt{stdout}) como los errores (\texttt{stderr}):
\begin{minted}{python} 
def generate(): 
    while True: 
    reads = [process.stdout, process.stderr] readable, _, _ = select.select(reads, [], []) 
    for stream in readable: 
        output = stream.readline() 
        if output: 
            yield output stream.flush() 
        if process.poll() is not None: 
            break 
    process.stdout.close() 
    process.stderr.close() 
\end{minted}

El problema era que la salida no se mostraba dinámicamente, y el usuario no podía saber si el proceso se estaba ejecutando correctamente hasta que este terminaba. Se intentó eliminar el búfer de salida para forzar el envío inmediato de los datos mediante el comando:
\begin{minted}{bash} 
stdbuf -oL snapper-ml --config_file nombre_config
\end{minted}

Aparentemente, este enfoque parecía funcionar, ya que la salida se mostraba de forma más dinámica. Sin embargo, se observó que parte de la salida se perdía debido a condiciones de carrera, un problema de sincronización donde las operaciones de lectura y escritura de datos ocurren de manera descoordinada. En este caso, las líneas de salida se escribían varias veces antes de enviarse, provocando que algunas se perdieran.

Para solucionar este problema, se consideró utilizar mecanismos de concurrencia como cerrojos y semáforos. Sin embargo, la solución definitiva implicó el uso de \textbf{expect}, una herramienta diseñada para scripts interactivos que permite gestionar el búfer de manera eficiente. Se instaló con:

\begin{minted}{bash} 
pacman -S expect # En Arch Linux 
apt-get install expect # En Ubuntu 
\end{minted}

Luego, se utilizó el comando \texttt{unbuffer} para ejecutar \Gls{snapperml} sin problemas de búfer:
\begin{minted}{bash} 
unbuffer snapper-ml --config_file nombre_config 
\end{minted}

\subsubsection{Funciones Asíncronas en React (\texttt{useEffect})}
A pesar de que la API ahora enviaba correctamente la salida, se seguían omitiendo partes en la web. Esto se debía al uso de \texttt{useEffect} en \texttt{Execute.tsx}, una función de React diseñada para ejecutar efectos secundarios en respuesta a cambios de estado. Aunque \texttt{useEffect} funciona bien en la mayoría de los casos, es asíncrona por naturaleza, lo que provocaba problemas de sincronización al manejar la salida de la API.

Para resolverlo, se reemplazó \texttt{useEffect} por un enfoque más controlado. Se expuso la función \texttt{writeOutput} (y \texttt{writeCommand}) y se llamó directamente después de la llamada a la API:

\begin{minted}{typescript} 
useImperativeHandle(ref, () => ({
    writeOutput,
    writeCommand: (command: string) => {
      xterm.current?.write(`${command}\n`);
    },
  }));
\end{minted}

Esto permitió actualizar la terminal interactiva en tiempo real, sin perder información, y garantizó que los datos de la API se procesaran correctamente. De esta forma, se solucionaron los problemas de sincronización y se mejoró la experiencia de usuario en la \acrshort{ui}.

\begin{minted}{python}

process_lock = threading.Lock()

Se utiliza el \texttt{mutex} tanto para añadir nuevos procesos al diccionario:

with process_lock:

\end{minted}

with process_lock:
    processes.pop(process_id, None) # Eliminar el proceso del diccionario global
